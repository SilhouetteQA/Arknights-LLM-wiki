# M0 store/ — Entity Registry + Source Index + Page Store

**日期:** 2026-06-15
**状态:** 已完成
**关联:** Phase 2 知识图谱生成，Layer 0 基础层

---

## 一、背景

Phase 2 从"提取驱动"转为"检索驱动"：用户问什么 → 需要什么 Wiki 页面 → LLM 一次性生成完整页面。

M0 是 Layer 0 基础层，负责三件事：
1. **Entity Registry** — 注册知识图谱中所有实体（干员角色、故事NPC、阵营、地区、概念），每个实体有唯一 ID，同一人物的不同形态/别名解析为同一 entity
2. **Source Index** — 维护"哪个实体出现在哪个源文档的哪个位置"的双向索引，同时支持精确匹配和概念层面匹配（如"深海猎人"关键词映射到概念实体）
3. **Page Store** — 存储和检索已生成的 Wiki 页面（9 种类型）

M0 是纯粹的 SQL + 规则，不依赖任何 LLM 调用。

---

## 二、目标

1. 设计并实现 SQLite 四表 schema（entities / entity_aliases / source_index / wiki_pages）
2. 实现类 Repository 接口（每表一个 Repository 类）
3. 从 Phase 1 全部数据（operators.json、index.json、stories/ 对话）完成初始种子注入，覆盖干员和故事 NPC
4. 支持实体别名解析（临光=耀骑士临光，W=维什戴尔）
5. 支持概念/关键词层面索引（深海猎人、岁兽等抽象概念）
6. 为 M1-M9 页面生成模块提供稳定的数据读写接口

---

## 三、不在此阶段的范围

- LLM 调用 — M1+ 才有
- Wiki 页面生成逻辑 — 由 M1-M9 各自负责，M0 只提供存储
- 向量化/检索 — M11 rag/ 负责
- Web 服务 — Layer 2

## 四、数据库设计

### 4.1 数据库文件

```
data/arknights_wiki.db
```

单文件 SQLite，四张主表。

### 4.2 表一：entities — 实体注册表

每个实体在知识图谱中有唯一标识。注意：同一人物的不同形态/名字应解析为同一个实体（通过 entity_aliases 表辅助）。

```sql
CREATE TABLE entities (
    id              TEXT PRIMARY KEY,      -- 格式: {type}:{slug}，如 "character:amiya", "faction:rhodes_island"
    type            TEXT NOT NULL,         -- character | faction | region | concept | event | storyarc | chapter
    name_zh         TEXT NOT NULL,         -- 中文名（规范名称）
    aliases         TEXT DEFAULT '[]',     -- JSON 数组，已知别名列表（种子阶段 + 后续 M3 补充）
    source_data     TEXT,                  -- JSON，从原始数据提取的基础元数据
    lifecycle       TEXT DEFAULT 'active', -- active | deprecated | merged_into:<target_id>
    created_at      TEXT DEFAULT (datetime('now')),
    updated_at      TEXT DEFAULT (datetime('now'))
);

CREATE INDEX idx_entities_type ON entities(type);
CREATE INDEX idx_entities_name ON entities(name_zh);
```

**关键变更 (v2 vs v1)：** 不再使用 `UNIQUE(name_zh, type)`。同一人物可能有多个名字（W / 维什戴尔），唯一性由 entity_id 保证，重名检测由应用层 + entity_aliases 表处理。

**实体类型说明：**

| type | 含义 | 种子来源 | 数量预估 |
|------|------|----------|----------|
| `character` | 干员 + 故事 NPC | operators.json + stories/ 对话角色名 | ~600+ |
| `faction` | 阵营/组织 | operators.json (logo/group) + 人工种子 | ~80+ |
| `region` | 地区/国家 | operators.json (nation/birth_place) + 人工种子 | ~60+ |
| `concept` | 核心概念 | 人工种子 + keyword 表驱动 (M2) | ~50+ |
| `event` | 重大事件 | LLM 提取 (M6) | 待定 |
| `storyarc` | 故事弧线 | index.json 分组 (M7) | ~50 |
| `chapter` | 章节 | index.json | ~108 |

`timeline` 和 `glossary` 不使用 entities 表，它们分别是纯时间戳条目和术语→概念映射，结构不同。

### 4.3 表二：entity_aliases — 实体别名解析表

解决"临光/耀骑士临光"、"W/维什戴尔"等同一人物不同形态的识别问题。

```sql
CREATE TABLE entity_aliases (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    alias_text      TEXT NOT NULL,         -- 别名文本（如 "耀骑士临光", "维什戴尔"）
    entity_id       TEXT NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    alias_type      TEXT DEFAULT 'alt_name', -- alt_name | title | form | nickname | codename
    UNIQUE(alias_text, entity_id)
);

CREATE INDEX idx_aliases_text ON entity_aliases(alias_text);
CREATE INDEX idx_aliases_entity ON entity_aliases(entity_id);
```

**查找逻辑：** 当匹配源文档中的名称时，先查 entity_aliases.alias_text，再查 entities.name_zh。两个表统一视为"已知实体名集合"。

**种子来源：** `config/identity_map.json`（人工维护的已知别名映射），格式：

```json
{
  "耀骑士临光": "character:lin_guang",
  "W": "character:w",
  "维什戴尔": "character:w",
  "浊心斯卡蒂": "character:skadi",
  "近卫阿米娅": "character:amiya",
  "Guard": "character:amiya"
}
```

### 4.4 表三：source_index — 源文档索引

双向索引：给定实体 → 找到所有相关源文档片段，给定源文档 → 找到所有涉及的实体。

```sql
CREATE TABLE source_index (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    entity_id       TEXT NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    source_type     TEXT NOT NULL,         -- story | operator_archive
    source_id       TEXT NOT NULL,         -- story node id 或 operator id
    source_location TEXT,                  -- 源文档内位置描述（如 "档案资料一", "对话行3"）
    match_type      TEXT DEFAULT 'exact',  -- exact | alias | concept_keyword | manual
    relevance       REAL DEFAULT 1.0,      -- 相关性权重 0.0-1.0
    source_text     TEXT,                  -- 匹配的源文本片段（用于后续 LLM 生成）
    created_at      TEXT DEFAULT (datetime('now')),
    UNIQUE(entity_id, source_type, source_id, source_location)
);

CREATE INDEX idx_src_entity ON source_index(entity_id);
CREATE INDEX idx_src_source ON source_index(source_type, source_id);
CREATE INDEX idx_src_match ON source_index(match_type);
```

**match_type 字段说明：**

| match_type | 含义 | 示例 |
|------------|------|------|
| `exact` | 实体 name_zh 精确出现在源文本中 | "阿米娅" 出现在对话行 |
| `alias` | 实体别名(aliases) 出现在源文本中 | "Guard" 出现在对话行 → 映射到 character:amiya |
| `concept_keyword` | 概念关键词匹配（非精确实体名） | "深海猎人血脉" → concept:abyssal_hunters |
| `manual` | 人工标注 | 后续 QA 补充 |

**索引建立规则（纯规则，无 LLM）：**

| 规则 | 优先级 | 说明 |
|------|--------|------|
| 精确名匹配 | 1 | entity.name_zh 或 entity_aliases.alias_text 出现在源文本 |
| 概念关键词 | 2 | 源文本包含概念关键词 → concept 实体 |
| 对话角色映射 | 3 | story node 对话行的说话角色名 → character 实体 |
| 档案归属 | 1 | 每个 operator archive → 对应 character 实体 |

### 4.5 表四：wiki_pages — Wiki 页面存储

存储已生成的完整 Wiki 页面。每个实体可以有多个版本（如重新生成）。

```sql
CREATE TABLE wiki_pages (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    entity_id       TEXT NOT NULL REFERENCES entities(id) ON DELETE CASCADE,
    page_type       TEXT NOT NULL,         -- character|faction|region|concept|event|storyarc|chapter|timeline|glossary
    version         INTEGER DEFAULT 1,
    content_json    TEXT NOT NULL,         -- JSON，结构化页面内容（各页面类型的 section 键值对）
    content_md      TEXT,                  -- Markdown 渲染版本
    source_refs     TEXT DEFAULT '[]',     -- JSON，引用的 source_index.id 列表
    quality_score   REAL,                  -- validate 操作的质量评分
    status          TEXT DEFAULT 'draft',  -- draft | published | deprecated
    generated_by    TEXT,                  -- 生成者标识（如 "M3:character" 或 "manual"）
    generated_at    TEXT DEFAULT (datetime('now')),
    updated_at      TEXT DEFAULT (datetime('now'))
);

CREATE INDEX idx_pages_entity ON wiki_pages(entity_id);
CREATE INDEX idx_pages_type ON wiki_pages(page_type);
CREATE INDEX idx_pages_status ON wiki_pages(status);
CREATE INDEX idx_pages_entity_version ON wiki_pages(entity_id, version DESC);
```

### 4.6 ER 关系

```
entities 1 ──── N entity_aliases (一个实体可有多个别名)
entities 1 ──── N source_index   (一个实体出现在多个源文档中)
entities 1 ──── N wiki_pages     (一个实体可以有多个版本的 Wiki 页面)
source_index 1 ──── N wiki_pages.source_refs (一个源片段被多个页面引用)
```

### 4.7 待 M1-M9 补充的表

以下表结构在 M0 阶段不实现，仅预留设计供后续模块使用：

- `entity_links` — 实体间关系（A 属于阵营 B，C 参与了事件 D）— 由 M3-M6 的 link 操作填充
- `glossary_entries` — 术语表（术语→简短定义→concept entity 链接）— M9 专用
- `timeline_entries` — 时间线（时间戳→事件描述→关联 entity）— M8 专用

## 五、Repository 接口设计

### 5.1 EntityRepository

```python
class EntityRepository:
    def __init__(self, db_path: str)

    # CRUD
    def insert(self, entity: dict) -> str           # → entity_id
    def update(self, entity_id: str, updates: dict)
    def delete(self, entity_id: str)

    # Query
    def get(self, entity_id: str) -> dict | None
    def get_by_name(self, name_zh: str, type: str) -> dict | None
    def list_by_type(self, type: str) -> list[dict]
    def search_by_name(self, name: str) -> list[dict]  # LIKE 模糊匹配
    def count(self, type: str | None = None) -> int

    # 别名管理
    def add_alias(self, entity_id: str, alias: str, alias_type: str = 'alt_name')
    def remove_alias(self, entity_id: str, alias: str)
    def get_aliases(self, entity_id: str) -> list[str]

    # 实体解析 — 给定一个文本中的名称，找到对应的规范实体
    def resolve_name(self, name: str, type: str = None) -> str | None  # → entity_id or None

    # Seed
    def seed_from_operators(self, operators_json_path: str) -> int  # → 插入数
    def seed_from_story_dialogue(self, index_json_path: str, stories_dir: str) -> int  # → 插入数（新增NPC）
    def seed_identity_map(self, identity_map_path: str) -> int      # → 插入别名数
```

## 六、数据种子策略（三来源 + 两配置）

M0 需要从 Phase 1 已有数据完成初始填充。种子是可重复运行的幂等操作。

### 6.1 种子来源一：operators.json → character/faction/region 实体

**entities 表：**
- 每个 operator → `character:{id}` 实体（id 使用干员编号，如 R001）
- 提取所有唯一的 logo → `faction:{slug}` 实体
- 提取所有唯一的 nation → `region:{slug}` 实体
- 提取所有唯一的 birth_place → `region:{slug}` 实体（与 nation 合并去重）
- 提取所有唯一的 team/group → `faction:{slug}` 实体

**source_index 表：**
- 每个 operator 的每段档案文本 → character entity + `operator_archive` 源类型

### 6.2 种子来源二：stories/ 对话 → story NPC character 实体（新增）

**这是 v2 的关键补充。** 故事对话中出现的角色名可能与干员列表重叠，也可能是纯 NPC（如塔露拉、魏彦吾、霜星等）。

**提取策略：**
1. 遍历 `data/stories/` 中所有 story JSON 的对话行
2. 从每行对话提取"说话角色名"（`lines[].speaker` 字段）
3. 对所有角色名去重

**NPC 过滤规则（重要）：**
大量角色名为泛型描述而非具体人物，必须过滤，不注册为实体：

| 过滤类别 | 关键词模式 | 示例 | 对话量 |
|----------|-----------|------|--------|
| 占位符 | `???`, `？？？`, `？` | 未知/隐藏角色 | ~4200 |
| 泛型职业 | 结尾含 `成员`, `士兵`, `队员`, `干员`, `佣兵`, `术师`, `术士`, `守卫`, `卫兵`, `军官`, `警员`, `警察`, `宪兵`, `骑士`, `教徒`, `信使`, `难民`, `赏金猎人` | 整合运动成员, 罗德岛干员, 维多利亚士兵 | ~3500 |
| 泛型描述 | 含 `居民`, `市民`, `村民`, `船员`, `路人`, `工人`, `学生`, `教师`, `商人`, `老人`, `少女`, `少年`, `小孩`, `孩子`, `男子`, `女子`, `妇人`, `老头`, `老太太`, `女孩`, `男孩`, `青年`, `中年`, `男性`, `女性` | 女性居民, 沉稳的青年, 男性居民A | ~2000 |
| 系统/旁白 | `系统`, `广播`, `旁白`, `合声`, `合唱`, `齐声`, `众人`, `一同`, `播音员`, `记者` | 广播, 众人 | ~500 |
| 泛型前缀 | 含 `带队的`, `带剑的`, `老练的`, `沉默的`, `高大的`, `年轻的`, `神秘的` + 职业名 | 带队的军官, 神秘的女性 | ~500 |

**过滤实现：** `_NPC_FILTER_PATTERNS` 正则在 `seed_from_story_dialogue()` 入口处执行，匹配任一模式则跳过。

**剩余 NPC 提取（过滤后）：**
4. 查 entity_aliases 表 → 如果已存在（干员或已知别名），跳过
5. 查 entities.name_zh → 如果已存在，跳过
6. 否则作为新 NPC 插入 → `character:{slug}` 实体，type=character

> 注意：标题式角色名（如 "烛骑士"、"血骑士"、"老骑士"、"逐魇骑士"）虽含"骑士"关键词，但可能是特定有名角色。此类边界情况暂时保留，由 M3 character 模块进一步判断是否应合并到规范实体。

**source_index 表：**
- 每条对话行 → 说话角色的 character entity + `story` 源类型 + source_text=对话内容
- 无名NPC的对话行**不建立** source_index（反正没有对应实体）

### 6.3 种子来源三：index.json → chapter 实体

**entities 表：**
- 每个唯一 chapter 值 → `chapter:{slug}` 实体

**storyarc 暂不处理** — 由 M7 负责将 chapter 聚合为 storyarc。

### 6.4 种子配置一：identity_map.json（自动提取 + 人工补充）

解决同人多形态问题（异格/升变/别名 → 规范实体）。

**来源：**
- **PRTS Wiki 自动提取**：从 `Category:异格干员` (37 个) + 各干员页 `alter-operator-list` 表提取异格→原型映射
- **operators.json 升变检测**：同一 operator ID 的多个形态（如阿米娅(医疗)、阿米娅(近卫) → R001）
- **人工补充**：已知别名（如 `Guard` → 阿米娅）

路径：`config/identity_map.json`

```json
{
  "_description": "PRTS Wiki 异格一览 自动提取 + 人工补充。key=异格/升变/别名，value=规范entity_id",
  "_source": "https://prts.wiki/w/Category:异格干员 (37 异格) + operators.json (升变)",
  "mappings": {
    "耀骑士临光": "character:KZ01",
    "维什戴尔": "character:B00W",
    "浊心斯卡蒂": "character:AA01",
    "假日威龙陈": "character:LM04",
    "阿米娅(医疗)": "character:R001",
    "阿米娅(近卫)": "character:R001",
    "Guard": "character:R001"
  }
}
```

种子时：遍历 `mappings`，将 key 插入 entity_aliases 表（alias_type='alt_name'），value 作为规范 entity_id。

### 6.5 种子配置二：concept_keywords.json（概念关键词 → 概念实体映射）

解决侧面描述、概括描写的索引问题。路径：`config/concept_keywords.json`

```json
{
  "_description": "概念关键词 → 概念实体的映射。种子时扫描源文档匹配这些关键词，建立概念级索引。",
  "keywords": [
    {
      "keywords": ["深海猎人", "阿戈尔猎人", "深海猎人血脉"],
      "entity_id": "concept:abyssal_hunters",
      "display_name": "深海猎人"
    },
    {
      "keywords": ["岁兽", "岁", "岁之碎片", "岁相"],
      "entity_id": "concept:sui",
      "display_name": "岁兽"
    },
    {
      "keywords": ["源石", "源石技艺", "源石结晶", "源石感染"],
      "entity_id": "concept:originium",
      "display_name": "源石"
    },
    {
      "keywords": ["矿石病", "矿石病感染", "感染者", "矿石病感染者"],
      "entity_id": "concept:oripathy",
      "display_name": "矿石病"
    },
    {
      "keywords": ["罗德岛", "罗德岛制药"],
      "entity_id": "faction:rhodes_island",
      "display_name": "罗德岛"
    },
    {
      "keywords": ["整合运动", "整合运动军", "整合运动成员"],
      "entity_id": "faction:reunion",
      "display_name": "整合运动"
    }
  ]
}
```

种子逻辑：
1. 遍历每个 concept_keyword
2. 确保对应的 concept/faction entity 在 entities 表中存在（不存在则创建）
3. 扫描所有 story JSON 和 operator archive 文本
4. 文本包含任一 keyword → 在 source_index 中建立 entry，match_type='concept_keyword'，relevance 根据匹配方式设置

**relevance 计算规则：**

| 匹配类型 | relevance | 说明 |
|----------|-----------|------|
| exact (实体名精确出现) | 1.0 | 强相关 |
| alias (别名匹配) | 0.9 | 强相关 |
| concept_keyword (关键词匹配) | 0.7 | 中等相关，概念层面 |
| manual (人工标注) | 1.0 | 人工确认 |

### 6.6 种子质量要求

- 种子阶段覆盖率目标：character 实体覆盖 operators.json 全部 + stories 对话中所有角色名
- 概念实体仅覆盖 `concept_keywords.json` 中定义的，更多由 M2 补充
- 重复检测：同一 entity_id INSERT OR IGNORE
- 种子运行幂等：重复执行不重复插入，不覆盖已有数据
- 种子顺序：先 entities → entity_aliases → source_index

## 九、风险与取舍

| 风险 | 应对 |
|------|------|
| NPC 识别遗漏 | 从 stories/ 对话角色名自动提取，覆盖全部出场角色 |
| 同人异名误拆 | identity_map.json 人工维护 + entity_aliases 表，种子前先加载别名映射 |
| 概念隐性描述漏索引 | concept_keywords.json 关键词驱动，关键字覆盖不到的由 M2 (LLM) 补充 |
| 概念关键词误匹配 | match_type='concept_keyword' + relevance=0.7 标记，方便后续人工过滤 |
| SQLite 写入并发 | M0-M9 全部单进程访问，不涉及并发写 |
| 实体 ID 冲突 | entity_id 由人工定义（seed 配置）或自动生成 slug（entities 表，name_zh 拼音化+去重后缀） |
